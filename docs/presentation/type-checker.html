Ao fim da fase 1, tudo depois do parser recusava classes com "not supported yet".

Agora o type checker aceita programas com classes e rejeita os mal tipados, antes de qualquer execução.

Antes da mudança

Duas funções e um ambiente

FunçãoRecebeDevolve
check_expruma expressão e o ambienteo tipo da expressão, ou um erro
check_stmtum statement e o ambienteum novo ambiente, ou um erro

O ambiente guarda o que já foi declarado: variáveis com tipo e mutabilidade, funções e ADTs.

val p = Point();   // adiciona p : Point
val px = p.x;     // usa p : Point

O programa é checado statement por statement, passando o ambiente adiante. O primeiro erro interrompe a checagem.

O ambiente ganha um lugar para classes

pub struct Scope<A> {
    pub variables: HashMap<Name, (bool, A)>,
    pub functions: HashMap<FuncSignature, Function>,
    pub adts: HashMap<Name, Vec<ValueConstructor>>,
    pub tests: IndexMap<Name, Function>,
    pub classes: HashMap<Name, Class>,
}

Mesmo padrão que já existia para ADTs e funções:

  • map_class: registra
  • lookup_class: procura do escopo mais interno ao global
  • get_all_classes: copia todas

O corpo de uma função é checado num ambiente novo. Sem copiar as classes para ele, uma função não enxergaria Point.

Passo a passo

Como o type checker verifica uma declaração de classe

Entrada
class Counter:
    var n: Int = 0;
    val step: Int = 1;
    def get(self: Counter) -> Int:
        return self.n;
    end;
    def twice(self: Counter) -> Int:
        return self.get() + self.get();
    end;
end
check_class_def_stmt
check_stmt
O statement é um ClassDef, que antes era recusado. Agora vai para check_class_def_stmt.
1. a classe é nova?
Counter não pode já existir. Ela é registrada antes dos membros, para que eles possam citá-la (self: Counter).
2. campos
Nomes não repetidos, tipo conhecido e valor inicial compatível: 0 é Int, como declarado.
3. assinaturas dos métodos
Nomes não repetidos, e o primeiro parâmetro tem que ser exatamente self: Counter.
4. corpos dos métodos
Só depois de conhecer todas as assinaturas. Por isso twice pode chamar get, e a ordem dos métodos não importa.
src/type_checker/expression_type_checker.rs

Point() continua sendo uma chamada de função

Para o parser, Point() e f() são iguais: um FuncCall. Ele não tem como saber se Point é uma classe.

O type checker tem essa informação no ambiente. Então check_func_call desvia quando o nome é uma classe:

if env.lookup_class(&func_name).is_some() {
    return check_instantiation(func_name, &exp_vector);
}
ExpressãoResultado
Point()TClass("Point")

Pont()erro: não é classe nem função

Sem nó New e sem mudar o parser. Construtor com argumentos fica para depois.

Dois ajustes de tipo

Nome de classe precisa existir, e [] cabe em List[Int]

check_type_is_known

O parser lê qualquer nome em posição de tipo como TClass. A fase 1 deixava passar erro de digitação:

def origin(p: Pont) -> Int: ...
[Type Error] unknown class 'Pont'.

Vale para parâmetros, retornos e campos, inclusive dentro de List, Maybe e tuplas.

type_fits

[] tem tipo List[Any] e Nothing tem tipo Maybe[Any]. Comparando por igualdade, nenhum dos dois caberia num campo:

var itens: List[Int] = [];
var melhor: Maybe[Int] = Nothing;

type_fits aceita Any dentro do tipo encontrado e, fora isso, exige o mesmo tipo.

src/type_checker/expression_type_checker.rs

O ponto exige uma instância de classe

obj.campo

  • O tipo de obj tem que ser uma classe
  • A classe tem que declarar o campo
  • Resultado: o tipo declarado do campo
c.n          // Int
c.z          // erro: Counter não tem campo z
(1).n        // erro: só instâncias têm campos

obj.metodo(args)

  • A classe tem que declarar o método
  • self já é obj: os argumentos se comparam com os parâmetros depois de self
  • Resultado: o tipo de retorno do método
c.add(2)     // Unit
c.add()      // erro: espera 1 argumento
c.add(True)  // erro: espera Int
src/type_checker/statement_type_checker.rs

Só campo declarado com var pode mudar

class Account:
    val id: Int = 1;
    var balance: Int = 0;
end;

val a = Account();
a.balance = 100;     // ok: balance é var
a.balance = "cem";   // erro: espera Int
a.id = 2;            // erro: id é val

check_field_assignment_stmt confere três coisas: o campo existe, é var e recebe um valor do tipo certo.

A mutabilidade é do campo, não da variável. a é val, mas a.balance = 100 é aceito: a variável continua apontando para o mesmo objeto, só o campo muda.
examples/classes/point_full.rpy

O programa da proposta, statement por statement

Programa
class Point:
    var x: Int = 0;
    var y: Int = 0;
    def init(self: Point,
             x: Int, y: Int) -> Unit:
        self.x = x;
        self.y = y;
    end;
    def get_x(self: Point) -> Int:
        return self.x;
    end;
end;
val p = Point();
p.init(3, 4);
val px = p.get_x();
assert(px == 3, "...");
Verificação
ambiente vazio
O type checker começa sem nada declarado.
check_class_def_stmt
Campos ok. No corpo de init, self.x = x: x é var Int e recebe Int. get_x devolve self.x : Int.
check_instantiation
Point é classe e não há argumentos: o tipo é Point.
check_method_call
init espera (Int, Int) depois de self. Recebe (Int, Int).
check_method_call
get_x não tem argumentos além de self e devolve Int.
check_assert
px == 3 é Boolean. Nenhum erro: o programa é bem tipado.
Ambiente
Point: x, y : var Int init, get_xp : val Pointpx : val Intprograma bem tipado

Por que assim

Decisões de projeto

DecisãoMotivo
self não é palavra reservadaReservar quebraria self: Point e self.x no parser. As regras de self ficam no type checker.
O parser aceita .campo em qualquer expressãoRestringir no parser quebraria f().y. O type checker rejeita ponto em quem não é classe.
Point() segue como FuncCallSaber se o nome é classe é informação semântica. O type checker consulta o ambiente, sem nó novo.
Assinaturas antes dos corposPermite que um método chame outro declarado mais abaixo.
Namespace únicoClasse, variável e função não podem ter o mesmo nome: Point() precisa ser inequívoco.
Defaults fechadosCampo não captura variável/função externa e não constrói diretamente a própria classe.
Type checker fora do cargo runOs exemplos antigos redeclaram _ várias vezes, e o type checker trata isso como erro.
